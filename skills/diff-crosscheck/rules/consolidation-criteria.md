# Rule 1 - 每項意見都要回到程式碼重新查證，不以多數決判定

- Level: `MUST`
- 對每項 reviewer 意見（摘要或圖表修正、finding 是否成立、嚴重性調整、新增 finding），都要回到固定 SHA 的程式碼與需求來源查證後，才決定是否採納。
- 兩個 reviewer 都同意，不代表成立；只有一方提出，不代表不成立。
- 主 agent 的草稿也只是其中一方的意見，不享有預設優先。
- 查證時套用 `criteria` 列出的規則，例如證據分級、finding 成立條件與嚴重性定義。

## Good Example

- 這個例子是好的，因為它不看票數，而是以程式碼查證結果決定。

```md
意見：Codex 認為 P1「逾時仍清空購物車」不成立（主張已有 guard）
查證：git show a1b2c3d:src/checkout/checkoutMachine.ts | sed -n '80,95p'
結果：guard 只涵蓋 NetworkError，TimeoutError 分支仍呼叫 clearCart() → 維持 P1
```

## Bad Example

- 這個例子是壞的，因為它以多數決取代查證。

```md
草稿與 subagent 都認為成立，Codex 認為不成立，二比一，維持成立。
```

# Rule 2 - 合併重複的 findings 並全域重新排序

- Level: `MUST`
- 同一根因、同一位置或同一修正方向的 findings 合併為一條；保留最完整的證據與所有位置。
- 每條 finding 標示提出者：草稿、Subagent、Codex；由多方獨立提出者，另標「多方佐證」。
- 合併後依嚴重性與影響重新排序整份清單，不保留各方原本的順序。

## Good Example

- 這個例子是好的，因為它把同一根因合併，並保留各方的證據與來源。

```md
### [P1] 逾時錯誤仍會清空購物車（提出者：草稿、Codex；多方佐證）
位置：checkoutMachine.ts#L88-L95（草稿）、CheckoutPage.tsx#L52（Codex 補充的呼叫端）
```

## Bad Example

- 這個例子是壞的，因為同一個問題以三種說法重複出現，讀者需要自己合併。

```md
- [P1] 逾時清空購物車（草稿）
- [P2] TimeoutError 分支呼叫 clearCart（Codex）
- [P1] 失敗後購物車消失（Subagent）
```

# Rule 3 - 查證屬實的摘要與圖表問題直接修正到最終版

- Level: `MUST`
- reviewer 指出摘要、功能分組、必要性說明或圖表與程式碼不符，且查證屬實時，直接修正最終報告的內容，不以附註方式保留錯誤版本。
- 被寫成事實的推測，改標【推測】或補上證據。
- 改動範圍或影響有遺漏或誇大時，修正對應的功能分組、圖中的節點與標記。

## Good Example

- 這個例子是好的，因為它直接修正圖與摘要，而不是在文末補充勘誤。

```md
Subagent：圖中「訂單摘要」標為 changed，但本次沒有修改該元件
查證：diff.patch 沒有 Summary.tsx 的 hunk，但它讀取 useCart().items → 改標為 affected，並在圖說補充受影響原因
```

## Bad Example

- 這個例子是壞的，因為錯誤的圖仍留在報告中，只在最後加註。

```md
註：reviewer 指出上圖「訂單摘要」應為 affected 而非 changed。
```

# Rule 4 - 排除不成立或屬偏好的意見，並記錄排除統計

- Level: `MUST`
- 下列意見查證後排除：不成立、僅屬個人偏好、工具已攔截、既有問題、與本次範圍無關。
- 嚴重性調整要依 `criteria` 中的嚴重性規則，按實際影響重新判定，不直接採用任何一方的等級。
- 在複核狀態中記錄排除的數量與類型；偏好類意見不必逐條列出。

## Good Example

- 這個例子是好的，因為它記錄了排除統計，讀者知道有哪些意見被過濾。

```md
排除 4 項：不成立 1（Codex：誤讀為未處理錯誤，實際在 L102 處理）、個人偏好 2、既有問題 1
```

## Bad Example

- 這個例子是壞的，因為意見被默默丟掉，讀者無從得知複核提出過什麼。

```md
（最終報告中沒有任何排除紀錄）
```

# Rule 5 - reviewer 新增的 finding 必須達到相同的證據門檻

- Level: `MUST`
- reviewer 新增的 finding 必須由主 agent 親自確認觸發路徑，並補上固定 SHA 位置連結、證據與最小修正方向，達到與草稿 findings 相同的完整度。
- 無法補足證據時，列入「待確認」或排除，不可原樣轉貼 reviewer 的文字。

## Good Example

- 這個例子是好的，因為它把 reviewer 的線索查證成完整的 finding。

```md
Codex 新增：重試按鈕在請求期間可重複點擊
查證：CheckoutPage.tsx#L64 的 disabled 只依 `isValid`，未含 `isSubmitting` → 確認可重複送出
補齊：觸發情境、影響（重複建立訂單）、位置連結、最小修正方向 → 列為 P1，提出者：Codex
```

## Bad Example

- 這個例子是壞的，因為它直接轉貼 reviewer 的一句話，沒有位置、情境或證據。

```md
- [P1] 按鈕可能重複點擊（Codex 提出）
```

# Rule 6 - 查證後仍無法判定的分歧列入待確認

- Level: `MUST`
- 查證後仍無法判定的分歧（例如需要執行期驗證、需求不明、依賴無法存取的外部系統），列入「待確認」。
- 每項待確認寫出：分歧點、各方主張、已查證的部分、缺少的證據，以及如何取得該證據。
- 不可為了讓報告看起來乾淨，而刪除或淡化無法解決的分歧。
- 分歧的對象若是仍符合成立條件的待驗證疑慮，保留在「建議修正」並維持其狀態，同時列入「待確認」，兩處互相引用。

## Good Example

- 這個例子是好的，因為它清楚交代分歧與缺少的證據。

```md
待確認：逾時後重試是否會重複扣款
- 草稿：P0 待驗證疑慮；Subagent：同意；Codex：認為後端會以訂單 ID 去重
- 已查證：前端重試以原購物車再次呼叫 `createOrder()`，未帶冪等鍵
- 缺少證據：後端是否支援冪等鍵（API 文件不在 repo 內）
- 取得方式：詢問後端或在測試環境重現
```

## Bad Example

- 這個例子是壞的，因為它把分歧簡化成一句話，讀者不知道缺少什麼才能下結論。

```md
待確認：重複扣款（意見不一致）
```

# Rule 7 - 複核狀態必須完整揭露執行情形與驗證缺口

- Level: `MUST`
- 每個 reviewer 寫出：狀態（完成、未完成、未執行）、未完成的原因（例如逾時、模型容量不足、未登入、用量上限）、依其回報實際執行的檢查、驗證限制；Codex 另依狀態 JSON 的 `attempts` 寫出實際使用的模型與重試經過。
- 統整處理寫出數量：合併、採納的修正、排除（含類型）、新增、待確認。
- 驗證缺口要向下傳遞：任一 reviewer 回報未驗證的面向，最終報告不可寫成已驗證。
- 最終報告的「報告狀態」與「複核結論」只能是：已完成雙重複核、僅完成單一複核（缺少：<reviewer>，原因：<原因>）、未經獨立複核。
- 原始複核結果不併入報告本文，只提供檔案路徑。

## Good Example

- 這個例子是好的，因為它讓讀者知道複核的實際涵蓋範圍與限制。

```md
- Subagent：完成。實際檢查：讀 diff 全部 hunk、checkoutMachine 修改前版本、3 個呼叫端。限制：未執行測試。
- Codex CLI：完成（gpt-6-astra，6 分 12 秒；gpt-5.6-sol 容量不足，接續重試 1 次仍失敗，改用備援模型 gpt-6-astra 接續完成）。實際檢查：git show / grep 共 14 次。限制：無法讀取 Jira 需求。
- 統整：合併 2、採納修正 3（圖 1、摘要 2）、排除 4（不成立 1、偏好 2、既有 1）、新增 1、待確認 1
```

## Bad Example

- 這個例子是壞的，因為它只寫「已複核」，看不出誰做了什麼、哪些沒驗證。

```md
已完成雙重複核，報告無誤。
```
