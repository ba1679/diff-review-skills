# Rule 1 - Finding 必須同時符合全部成立條件

- Level: `MUST`
- 一個問題只有在下列條件全部成立時，才能列為 finding：
  - 有實際影響：影響正確性、需求、安全性、資料、效能，或造成具體的維護風險。
  - 由本次改動引入或惡化：既有問題不列入，除非本次改動讓它被觸發或影響範圍擴大；主張「本次削弱了既有保護」時，必須比對修改前版本，確認修改前確實較強。
  - 觸發情境可由程式碼說明：能指出什麼輸入、操作或時序會導致什麼錯誤結果。
  - 具體可執行：能指出位置與最小修正方向。
  - 作者知道後很可能會修。
- 下列情況不列為 finding：
  - 純風格偏好或寫法差異。
  - lint、型別檢查或 formatter 已經攔截的問題。
  - 有說明理由的停用註解（例如 lint-ignore 附理由）。
  - 需求或 PR 明確說明的刻意行為改變。
  - 規格或設計文件中已接受的限制。
  - 本次未修改、也未因本次改動而受影響的程式碼。
  - 只有「可能會」而指不出觸發路徑的推測性擔憂。
- 不可為了湊數產出 findings；沒有符合條件的問題時，就寫沒有。

## Good Example

- 這個例子是好的，因為它逐項套用成立條件，並排除了不符合的項目。

```md
候選：逾時後重試以原購物車再次建立訂單，未帶冪等鍵
- 實際影響：重複扣款風險 ✔；本次引入：新增的 retry 未帶冪等鍵 ✔
- 觸發情境：付款 API 逾時 → 點重試 → 再次呼叫 `createOrder()` ✔；位置與修法明確 ✔ → 成立（待驗證疑慮：後端是否去重未證實）
候選：`OrderCard` 使用 function 宣告而非 arrow function → 純風格偏好 → 排除
```

## Bad Example

- 這個例子是壞的，因為它把無法指出觸發路徑的擔憂與既有問題都列成 finding。

```md
- 這裡未來可能會有效能問題
- `utils/http.ts`（本次未修改）的錯誤處理不夠完整
```

# Rule 2 - 嚴重性依 P0 到 P3 的定義判定

- Level: `MUST`
- P0 緊急：重大安全問題（可被利用的注入、金鑰外洩、權限繞過）、資料損失或損毀、核心服務不可用（主要頁面無法使用、無法登入、主流程完全中斷）。
- P1 高：主要功能錯誤、重要需求未達成或與驗收條件矛盾；應於合併前修正。
- P2 中：特定情境下的錯誤、具體的維護風險（例如同一規則的第二份實作、會不同步的第二份事實來源）、違反 repo 明文規範（包含 repo 內規格與設計文件的明文要求）。
- P3 低：不阻擋合併的改善建議。

## Good Example

- 這個例子是好的，因為每個等級都對應定義中的影響類型。

```md
- P0：逾時後重試未帶冪等鍵，若後端未去重會重複扣款（資料與金錢損失）
- P1：驗收條件要求失敗後保留購物車，實作在逾時錯誤時仍清空（重要需求未達成）
- P2：新增 `formatPrice` 與既有 `formatCurrency` 承載同一規則，日後幣別規則會分歧（具體維護風險）
```

## Bad Example

- 這個例子是壞的，因為等級和定義對不上：風格問題被列為高、資料損失卻被列為中。

```md
- P1：變數命名不夠清楚
- P2：重試會重複扣款
```

# Rule 3 - 先寫觸發情境與影響，再依實際影響決定等級

- Level: `MUST`
- 決定等級前，先寫出觸發情境與影響；等級由影響範圍（多少使用者或情境）、嚴重程度（錯誤、資料、安全）、發生機率與是否有替代路徑決定。
- 不可因為違反 best practice、慣例或「看起來不好」就升級；違反 repo 明文規範預設為 P2，除非造成更高的實際影響。
- 不可因為 findings 只有一個就提高等級，也不可因為 findings 很多就降低等級。
- 受審 repo 的流程（例如 push gate、CI 規則）會攔下同類問題時，在 finding 中註明，但等級仍依實際影響判定。

## Good Example

- 這個例子是好的，因為它先描述影響再定等級，並另外註明 repo 流程的處理方式。

```md
新增 `formatPrice` 與既有 `formatCurrency` 重複：目前輸出相同，但幣別規則改變時會分歧 → P2
註：此 repo 的 AGENTS.md 規定重複元件在 push 前審查會被擋下。
```

## Bad Example

- 這個例子是壞的，因為它只因為「不符合最佳實踐」就給高等級，卻沒有任何影響描述。

```md
P1：沒有使用 useCallback，不符合 React 最佳實踐。
```

# Rule 4 - 必須區分確定問題與待驗證疑慮

- Level: `MUST`
- 確定問題：觸發路徑已由程式碼證實，必要時加上已讀的呼叫端、測試或修改前版本。
- 待驗證疑慮：有具體懷疑但缺少關鍵證據，例如需要執行期行為、外部 API 的實際回應或無法讀取的需求文件。
- 待驗證疑慮仍可標示嚴重性，但必須寫出缺少的證據與驗證方式；不可把待驗證疑慮寫成確定問題的語氣。

## Good Example

- 這個例子是好的，因為它清楚說明缺少什麼證據與如何驗證。

```md
狀態：待驗證疑慮（P0）
懷疑：付款 API 逾時時可能已成功扣款，重試會重複扣款。
缺少證據：無法得知付款 API 是否以 idempotency key 去重（API 文件不在 repo 內）。
驗證方式：確認後端是否接受 `Idempotency-Key` header，或在測試環境重現逾時後重試。
```

## Bad Example

- 這個例子是壞的，因為它沒有證據卻用確定的語氣下結論。

```md
P1：重試一定會重複扣款，必須修正。
```

# Rule 5 - 每個 finding 的欄位內容都必須可查證

- Level: `MUST`
- 標題是一句話結論，讀者只看標題就知道問題是什麼。
- 觸發情境寫出具體的輸入、操作或時序；影響寫出使用者或系統會看到的結果。
- 證據至少包含：固定 SHA 的程式碼引用；涉及需求時引用需求原文；能重現的唯讀檢查指令（例如 `git show <sha>:<path> | sed -n '40,46p'`、`git grep -n <pattern> <sha>`）。本次納入未提交改動時，head 端改在工作目錄搜尋與閱讀（例如 `git grep -n --untracked <pattern>`），引用依 evidence 規則的工作目錄指紋格式。
- 位置使用固定 SHA 的 permalink（無 `repo.link_base` 或未提交改動時依 evidence 規則改用 `path:line`）；同一根因散在多處時，合併成一個 finding 並列出全部位置。
- 最小修正方向只寫解決此問題所需的最小改動，不順帶要求重構。
- 依據 repo 規範提出時，寫出規範檔案、條目與原文一句。

## Good Example

- 這個例子是好的，因為每個欄位都可以被他人獨立查證。

```md
### [P1] 逾時錯誤仍會清空購物車
- 狀態：確定問題
- 觸發情境：付款 API 回傳 504 → `submit.catch` 進入 `TimeoutError` 分支
- 影響：使用者重試前購物車已被清空，需重新選購
- 證據：[checkoutMachine.ts#L88-L95](...) 在 TimeoutError 分支呼叫 `clearCart()`；驗收條件「失敗後保留購物車」（PR 描述第 2 點）
- 檢查指令：`git show a1b2c3d:src/checkout/checkoutMachine.ts | sed -n '88,95p'`
- 最小修正方向：移除 TimeoutError 分支中的 `clearCart()`
```

## Bad Example

- 這個例子是壞的，因為標題、情境與修法都無法查證，也沒有位置。

```md
### 購物車邏輯有問題
結帳時購物車行為怪怪的，建議重新設計整個結帳流程。
```

# Rule 6 - 依嚴重性排序，沒有問題的級別省略

- Level: `MUST`
- findings 依 P0、P1、P2、P3 排序；同一級別內依影響大小排序。
- 沒有 finding 的級別直接省略，不寫「P0：無」。
- 完全沒有 finding 時，寫「未發現需修正的問題」，並列出已檢查的維度，讓讀者知道審查涵蓋了哪些面向。

## Good Example

- 這個例子是好的，因為它沒有 finding 時仍交代審查涵蓋範圍。

```md
## 3. 建議修正
未發現需修正的問題。已檢查：正確性、需求符合度（依 PR 描述 3 項驗收條件）、專案規範（AGENTS.md）、複用與 DRY、維護性；條件維度 a11y（觸發：新增按鈕）。
```

## Bad Example

- 這個例子是壞的，因為它列出空級別，並為了填滿而加入低價值建議。

```md
P0：無。P1：無。P2：無。
P3：可以考慮加更多註解；可以考慮改變數名稱。
```
